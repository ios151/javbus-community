# javbus-community

[JavBus（Scripting 脚本）](../scripting/scripts/JavBus/README.md)的**社区推荐服务**：一个 Cloudflare Worker + D1 数据库，自带管理后台，
让一群人一起维护「作者精选」和「网友推荐」两份推荐列表。Hono 框架，免费版就能跑。

> **状态**：代码和测试都写完了（320 个后端测试 + 173 个后台页面的测试，全部本地通过；后台页面在浏览器里逐页走过；脚本侧对着本地 Worker 跑过端到端；还经过一轮独立的代码审查，发现的问题都修了）。
> **已经在作者自己的 Cloudflare 免费账号上部署过一次（2026-10-23）**：线上的公开接口、后台页面、数据库迁移都正常，Worker 带着 `Referer` 从 JavBus 取封面也是通的（后台的封面就是这样取来显示的）；还没观察过的有——定时任务在平台上的实际触发、免费版 CPU 的真实占用。
> 你要自己部署一份，步骤见下面，大约 10 分钟。改了什么见 [CHANGELOG.md](CHANGELOG.md)。

## 它解决什么问题

JavBus 脚本里的「推荐」原来全靠原作者一个人：列表放在他的 GitLab 上，网友推荐的上传服务是他的 Google Apps Script。
2026-10-22 实测那个上传服务已经坏了（脚本里写 GitLab 用的令牌过期，上传一律失败），也没有别人能修。

这个项目把它换成大家一起维护的版本：

- **没有单点**：多个维护者各自有账号和角色，原作者的列表可以一键导进来；
- **有人把关**：网友提交可以先审核再公开；多人举报自动隐藏；有屏蔽词、网站名单、封禁、限频；
- **自己会体检**：定时去看每个条目的封面和详情页链接还在不在，失效了自动隐藏、恢复了自动放回；
- **和脚本无缝**：上传 / 撤销接口和原作者的 Apps Script 兼容，脚本里只要在设置里填一个地址。

## 功能

**给 App（脚本）用的公开接口**（`/api/v1`，不要登录）：读两份列表（带 `ETag`，没变回 304）、提交 / 撤销推荐、举报、测试连接。
提交者可以不用口令撤销自己提交的推荐（按随机设备号认人，服务端只存加盐哈希）。接口细节见 [docs/api.md](docs/api.md)。

**给维护者用的管理后台**（根路径 `/`，Preact 单页应用）：

| 页面 | 干什么 |
| --- | --- |
| 概览 | 待审 / 举报 / 失效数量、两份列表各多少条、最近一次检查、30 天新增趋势 |
| 审核队列 | 新提交先审核再公开（单条 / 批量通过、拒绝，可以先「检查这几条」再决定） |
| 条目管理 | 搜索、筛选（频道 / 状态 / 检查结果 / 被举报）、排序、新增、编辑、移到另一个频道、通过 / 隐藏 / 拒绝 / 删除、批量操作 |
| 举报 | 按条目合并显示举报原因，一键隐藏 / 驳回 / 删除 |
| 自动检查 | 最近的检查记录；「检查一批」「全部检查」（带进度，可中途停止）；失效和存疑的条目待复核 |
| 站点设置 | 站点名称、维护模式、收稿规则、限频、屏蔽词、网站名单、自动检查的各项参数 |
| 团队 | 账号、角色、停用、重置密钥 / 二次验证；邀请链接 |
| 封禁 | 封设备 / IP / 番号，可以顺手清掉对方已有的条目 |
| 操作日志 | 谁在什么时候做了什么（保留天数可调） |
| 导入导出 | 导出 / 导入 JSON；一键导入原作者在 GitLab 上的两份列表 |
| 我的账号 | 换访问密钥、二次验证（TOTP）、生成给脚本用的 App 口令 |

**定时任务**：每 30 分钟检查一批条目；每天凌晨清理过期数据、重建公开快照（自愈）。

## 架构

```
 JavBus 脚本 ──GET/POST──▶ /api/v1/*  ┐
                                        ├─ Hono 路由（src/）── D1（条目、账号、举报、设置、日志…）
 维护者浏览器 ──────────▶ /api/admin/* ┘        ▲
        │                                        │
        └─ 页面本身是静态文件（admin/dist，Workers 静态资源直接托管，不经过 Worker 代码）
                                            Cron：每 30 分钟检查一批 / 每天凌晨清理
```

- **一个 Worker 搞定**：API 和后台页面同一个域名，没有跨域；`/api/*` 先进 Worker，其余路径由静态资源托管（单页应用回退到 `index.html`）。
- **为什么页面不放 Pages**：Cloudflare 现在推荐新项目用「Workers + 静态资源」代替 Pages（功能是 Pages 的超集）。构建出来就是普通静态文件，
  真想放 Pages 也行，见下面「用 Pages 托管后台」，但不推荐。
- **公开列表是一行快照**：条目一变就在同一个事务里用 SQL 重建对应频道的 JSON，App 读列表只读这一行（附 `ETag`），Worker 不用在 CPU 里拼 JSON。
- **没有密码**：登录用 256 位随机的「访问密钥」（库里只存 SHA-256），可选再加 TOTP 二次验证。免费版每个请求只有 10 毫秒 CPU，PBKDF2 这类慢哈希根本放不进去；
  随机密钥本来也不需要慢哈希。
- 设计取舍和免费版额度怎么影响了写法：[docs/architecture.md](docs/architecture.md)。

## 快速开始（本地开发）

需要 Node.js 22+。

```bash
cd javbus-community
npm install
cp .dev.vars.example .dev.vars        # 里面的 SETUP_TOKEN 是首次创建站长用的口令，本地随便写
npm run db:migrate:local              # 在本地 D1 里建表
npm run build:admin                   # 构建后台页面（admin/dist）
npm run dev                           # = wrangler dev，打开 http://localhost:8787/ ，页面和 API 同一个地址
```

第一次打开会进「首次安装」页：填 `.dev.vars` 里的 `SETUP_TOKEN` 和你的名字，创建站长，**页面上显示的访问密钥只出现一次，存好**（以后登录就用它）。
造点假数据看效果：`node scripts/seed-dev.mjs`（见文件头注释；会建站长 / 管理员 / 协管三个账号、各种状态的条目、举报、邀请、封禁，并把三个访问密钥存到 `.wrangler/dev-keys.json`，方便验证不同角色看到的菜单）。
本地开发有个怪处：本地没有 Cloudflare 边缘写的 `CF-Connecting-IP`，所有请求算同一个 IP，所以**举报永远凑不够「3 个不同 IP」的自动隐藏阈值**——种子脚本自己带了这个请求头来模拟不同的人；想手动试自动隐藏，可以在设置里把「举报自动隐藏」调成 1。改后台页面想要热更新：另开一个终端 `npm run dev:admin`（Vite，5173 端口，`/api` 代理到 8787）。

```bash
npm run typecheck      # wrangler types + tsc（Worker）+ tsc（后台页面）
npm test               # 后端测试：本地模拟的 Workers 运行时 + D1，外连用 msw 模拟
npm run test:admin     # 后台页面里纯逻辑的测试
```

## 部署到 Cloudflare

你需要：一个 Cloudflare 账号（免费的就行）、Node.js 22+。下面的命令都在 `javbus-community/` 目录里执行。

1. **登录**：`npx wrangler login`（会打开浏览器授权）。
2. **（可选）改名字**：`wrangler.jsonc` 里的 `name` 就是 Worker 的名字，默认地址是 `https://<name>.<你的子域>.workers.dev`。
3. **第一次部署**：`npm run deploy`。它会：构建后台页面 → `wrangler deploy` → 应用数据库迁移。
   - 第一次部署时 Wrangler 发现 `d1_databases` 里没有 `database_id`，会按 `database_name` **自动帮你建库**（2026-10-23 在非交互环境里实测过，建库和迁移都一次成功）。
     在交互式终端里它还会把 `database_id` 写回 `wrangler.jsonc`（可以提交保存，也可以丢掉）；CI 这类非交互环境不写回。之后的部署不需要 `database_id`：
     Wrangler 会沿用 Worker 上已经绑定的同名库（2026-10-23 第二次部署实测：输出里是 `env.DB (inherited)`，没有再建库）。
     如果你的 Wrangler 版本没有自动建库，手动建：`npx wrangler d1 create javbus-community`，把输出里的 `database_id` 填进 `wrangler.jsonc`，再 `npm run deploy`。
   - 第一次还会问你要不要注册一个 `workers.dev` 子域名，按提示来。
4. **设置创建站长用的口令**：`npx wrangler secret put SETUP_TOKEN`，粘贴一串长随机字符（比如 `node -e "console.log(require('crypto').randomBytes(24).toString('hex'))"` 生成的）。
   它只用于首次创建站长，创建完就没用了；这个口令没设的话后台会告诉你「服务端还没有设置 SETUP_TOKEN」。
5. **创建站长**：打开 `https://<name>.<子域>.workers.dev/`，填 `SETUP_TOKEN` 和名字，创建站长。**访问密钥只显示一次**，存进密码管理器。
   建议马上去「我的账号」开二次验证。
6. **导入原作者的列表（可选）**：后台左侧「导入导出」→「导入原作者的列表（GitLab）」：先点「作者精选 ← Rec」，服务器下载完显示条数，「导入后的状态」选「直接上线」再点导入；
   等进度走完，再点「网友推荐 ← RecBot」照样来一遍。服务器下载失败的话，在浏览器里打开卡片上列出的两个地址、另存成文件，用同一页的「从文件导入」——
   原作者的列表不带频道，默认进「网友推荐」，导 `Rec` 那份时要把「导入到」改成「作者精选」。
7. **调设置**：后台「设置」，至少看一眼「网友推荐直接上线」要不要关（关了 = 先审核再公开）、限频、屏蔽词。
8. **邀请别的维护者**：后台「团队」→ 新建邀请，把生成的链接发给对方（有效期默认 7 天，用一次就作废）。
9. **接到脚本**：见下面。

之后升级：`git pull`（或自己改了代码）→ `npm install` → `npm run deploy`。**表结构只增不改**：要改表就新增 `migrations/0002_xxx.sql`，
绝不要改已经部署过的 `0001_init.sql`。有新迁移时想让新旧代码都不出错，先 `npm run db:migrate` 再 `npm run deploy`。

### 接到 JavBus 脚本

两种方式，任选：

- **每个用户自己填**：脚本「设置 → 推荐服务 → 社区服务地址」，填 `https://<name>.<子域>.workers.dev`（不带末尾斜杠），点「测试连接」应该显示「连接成功：…」。
- **开箱即用**：把地址写进脚本的 `core/constants.ts` 的 `COMMUNITY_URL` 再发版，所有没改过这项设置的用户自动用上（现在的脚本已经填好了作者部署的这一份）。

**接管哪几份列表**由脚本 `core/constants.ts` 的 `COMMUNITY_CHANNELS` 决定，出厂只有 `["user"]`：网友推荐走这个服务；作者精选仍然读原作者 GitLab 上的列表，
「作者推荐」也仍然走原作者的上传服务。所以后台里的「作者精选」频道目前用不上，不导入也没关系；以后想搬过来，先导入作者精选，再把 `"author"` 加进 `COMMUNITY_CHANNELS` 发版。

维护者想在脚本里撤销别人提交的网友推荐：后台「我的账号 → App 口令」生成一个（`jca_` 开头），脚本里弹出输入框时填它。作者精选不归这个服务管的时候，脚本里的「作者推荐」用不上这个口令。
脚本侧的行为（设备号、自助撤销、举报、返回码）见 [脚本 README 的「社区推荐服务」](../scripting/scripts/JavBus/README.md)。

### 用 GitHub Actions 自动部署（可选）

仓库里有两个工作流：`.github/workflows/ci.yml`（推送 / PR 时跑类型检查和全部测试）和 `deploy.yml`（手动触发时部署；打开下面第 4 步的开关后，推送到 `main` 也自动部署）。要用 `deploy.yml`：

1. **先在自己电脑上手动 `npm run deploy` 一次**，把 Worker 和 D1 库建出来。之后 CI 里部署不需要 `database_id`：Wrangler 会沿用 Worker 上已经绑定的同名库（本机第二次部署实测会沿用；真实 CI 里没跑过）。
   想把 id 写死也行：`npx wrangler d1 list` 查到 id，填进 `wrangler.jsonc`。
2. 在 Cloudflare 的 My Profile → API Tokens 里建一个令牌：用「Edit Cloudflare Workers」模板，并确认包含 **D1 的编辑权限**（没有就加上），
   再把令牌和账号 ID 存进仓库 Settings → Secrets and variables → Actions：`CLOUDFLARE_API_TOKEN`、`CLOUDFLARE_ACCOUNT_ID`。
3. `SETUP_TOKEN` 不在 CI 里：它是 Worker 自己的机密，`wrangler secret put` 设一次，之后部署不会清掉。
4. 想推送到 `main` 就自动部署：在同一页的 **Variables** 里加 `DEPLOY_TO_CLOUDFLARE`，值填 `true`。没加的话，推送触发的部署任务显示为「跳过」（免得机密还没配好时每次推送都报错）；
   手动运行（Actions → Deploy → Run workflow）不看这个开关。

> `ci.yml` 每次推送都会跑；`deploy.yml` 还没在真实仓库里部署过（要先配好机密）。

### 网络和域名

- `workers.dev` 在部分网络下访问不稳定甚至打不开（脚本用户和维护者都会受影响）。想稳一点，给 Worker 绑一个自己的域名：
  Cloudflare 后台 → Workers & Pages → 你的 Worker → Settings → Domains & Routes → Add → Custom domain（域名要托管在 Cloudflare）。
  绑好以后脚本里填新域名就行。这一点我没法替你验证，是常见情况下的建议。
- 想给后台再加一层访问控制，可以用 Cloudflare Access 保护后台的页面和 `/api/admin/*`（只放行你们的邮箱），**`/api/v1/*` 必须保持公开**，脚本要直接访问它。
  这个我没有试过；后台自己的登录（访问密钥 + 可选 TOTP）本来就够用，这层是额外的。

### 用 Pages 托管后台（不推荐）

后台页面构建出来（`npm run build:admin` → `admin/dist`）就是普通静态文件，可以 `npx wrangler pages deploy admin/dist` 放到 Pages 上。
但后台的请求是同源的（`/api/admin/*`，登录 cookie 是 `SameSite=Strict`，并且服务端会校验 `Origin` 和本站一致），所以 Pages 的域名下 `/api/*` 必须转发到这个 Worker——
最简单的做法是给两者绑**同一个自己的域名**：`你的域名/api/*` 走 Worker 路由，其余走 Pages。这条路我没有实际部署验证过，也比 Workers 静态资源麻烦；
除非你已经有 Pages 项目要复用，否则用默认的方案。

## 维护者指南

### 角色

| 角色 | 能做什么 |
| --- | --- |
| 协管 | 审核条目（新增 / 编辑 / 通过 / 拒绝 / 隐藏 / 删除）、处理举报、手动检查一批或指定条目、看操作日志 |
| 管理员 | 协管的一切 + 改站点设置、封禁、导入导出、全部检查、看账号和邀请、邀请协管 |
| 站长 | 管理员的一切 + 管理所有账号（邀请管理员、改角色、停用、重置密钥 / 二次验证） |

权限矩阵只有一份（`shared/types.ts` 的 `can()`），后端的接口检查和后台页面里的显示 / 隐藏用的是同一个函数。

### 日常

- **待审**：把「网友推荐直接上线」关掉的话，新提交都在这里；不处理的会在 14 天（可调）后自动拒绝。拿不准的先点「检查这几条」看封面和链接还在不在。
- **举报**：一个网友推荐的条目被 3 个**不同的 IP**（可调；IPv6 按 /64 一段算一个）举报，会自动隐藏、出现在举报页等你复核：**隐藏**（确认有问题）、**驳回**（没问题，会恢复上线）、**删除**。
  人数按 IP 算而不是按设备号：设备号是 App 自己报的、谁都能编，换几个设备号不算多个人。**作者精选不会被自动隐藏**（匿名举报不能直接下架维护者挑的），只进待复核、举报数照常显示。
  你「通过」一个被自动隐藏的条目时，没处理的举报算驳回、举报数清零，不会下一个人一举报就又被隐藏。
- **检查**：看「失效」和「存疑」的条目。失效 = 封面或链接返回 404 / 410；存疑 = 其它情况（403、验证页、超时、封面返回了网页……），**只做标记不隐藏**，需要你人工看一眼。
- **封禁**：条目里显示的「提交者」「IP」是加盐哈希，点「封禁提交者」会带着它跳到封禁页；勾「同时清理对方已有条目」会把对方已上线的隐藏、待审的拒绝。
- **邀请**：邀请链接只显示一次，一次有效，默认 7 天过期，同时最多 20 个有效邀请。

### 自动检查是怎么工作的

每 30 分钟（定时任务）按「最久没查的 / 从没查过的优先」挑一批，对每个条目的封面地址和详情页地址各发一次请求：

| 结果 | 含义 | 后果 |
| --- | --- | --- |
| 失效 | 封面或链接返回 404 / 410 | 连续失效达到阈值（默认 3 次）才自动隐藏 |
| 存疑 | 403 / 429 / 5xx、超时、网络错误、封面返回了网页（防盗链页）…… | 只标记；不加也不清零「连续失效」的计数 |
| 正常 | 2xx（封面还要求返回的是图片） | 清零「连续失效」；因失效被自动隐藏的会自动放回来 |
| 没法检查 | 详情页被站点的年龄验证页挡住（见下） | 这一项不参与判定，只看另一项（封面）；一项都没法判断（只剩被挡住的链接，或根本没有可查的地址）时记成「没查成」——不是「正常」：不会清零失效计数，也不会触发自动恢复 |

几个要知道的限制：

- 站点常有 Cloudflare 验证页，机器访问被拒（403）是常事，所以 403 只算「存疑」，**不会**因此隐藏——但也意味着这类站点上真正失效的条目要靠人工看。
- 免费版一次调用最多 50 个子请求、每个条目最多 2 个，所以一批**最多 25 个**（设置里「每次检查几个条目」，默认 10，上限 25）；子请求额度用完时没发出去的条目这次不算查过（记录里会写）。
  每天最多查 `批量 × 48` 个：3000 条、批量 10 的话查完一轮要 6 天多；想更快把批量调到 25。「复查间隔」只是下限，不是保证。
- 自动隐藏有三道保险（误判的代价是整站条目被下架）：① 连续失效达到阈值才隐藏；② 「连续」要隔得开——两次失效之间至少隔半个复查间隔才都算数，手动连点几次「检查一批」凑不够；
  ③ 一批里几乎全判成失效（≥ 5 条且 ≥ 80%），多半是站点在拦我们或网络出了问题，整批改判「存疑」、不累计。手动指定几个条目来查时不做第 ③ 条。
- 「检查」页的「全部检查」是前端反复调用接口（每次一批），不受定时任务的限制，适合刚导入完一大批之后手动扫一遍。
- 「检查」页的运行记录里，某一行带着「未完成」说明这一轮还没收尾：要么还在跑，要么 Worker 中途被平台掐了；超过 1 小时还没收尾的，每天的清理会把它标成「中途中断」。
- 检查时用的是手机 Safari 的 UA，封面请求带上详情页所在站点的 `Referer`（有的站有防盗链）。
- **JavBus 的详情页没法直接检查**（2026-10-22 用 curl 打真站实测）：没有年龄验证 cookie 时，所有详情页——不管番号存不存在——都会 302 到 `/doc/driver-verify` 并返回 200，
  所以检查器看不到真实页面，「链接返回 200」是假信号。我们**不替检查器去带验证 cookie 绕过它**（脚本那边也是「先问用户、同意才提交」，不静默绕过），
  而是认出验证页、把这一项记成「没法检查」，**对 JavBus 实际上只检查封面**：存在的封面是 `206 image/jpeg`，不存在的是 `404`，不带 `Referer` 是 `403`（防盗链，所以检查器带着它）。
  封面一般随影片页一起被站点删掉，这个信号够用；真要检查详情页，得让维护者提供一个已通过验证的 cookie——没做。
- Cloudflare 的 Worker 带着 `Referer` 去取 JavBus 的封面是通的（2026-10-23 线上实测：后台的封面经服务端代理能显示，用的是同一种请求）。
  没验证的：定时检查在线上跑出来的实际结果、`dmmsee.bar` 这类镜像域名（我这边连不上，原作者的网友推荐里有）。测试里的各种响应是 msw 模拟的。

### 账号安全

- 访问密钥当密码保管。它只在创建账号 / 重置时显示一次，服务端只存哈希，丢了只能让站长重置。
- 强烈建议所有维护者开二次验证（TOTP，Google Authenticator / 1Password / Authy 都行）。开了以后登录要「密钥 + 6 位验证码」，验证码 10 分钟内最多试 5 次（先占名额再校验，并发猜也没用），输对了清零。
  已知局限：同一个验证码在有效期内可以重复使用（没做一次性保护）。
- App 口令（`jca_`）是给脚本用的，权限等于「审核条目」；每个人自己生成、自己管理、随时可以撤销；账号被停用时它们自动失效；
  站长在「团队」里**重置某人的访问密钥**时，他的 App 口令也会一并撤销（账号被盗期间攻击者生成的口令不能留着）。自己换密钥不撤，口令由本人单独管理。
- 邀请的权限跟着发邀请的人走：他被停用 / 改了角色，他发出去还没用的邀请作废；他发的管理员邀请，要他现在还是站长才能用。
- 名字会先规整（全角字母 → 普通字母），不能含看不见的字符；`system`、`app` 是保留名（操作日志里它们表示定时任务和脚本里的提交）。
- 别清空 `settings` 表：加盐哈希用的盐存在里面，清了会重新生成，之前所有的封禁和「自己撤销自己提交的」都对不上了。
- 一个人换了手机丢了验证器：站长在「团队」里点「重置二次验证」。丢了访问密钥：站长点「重置密钥」，会生成新的并踢掉对方所有会话。

### 备份与恢复

- **后台「数据 → 导出」**：下载全部条目的 JSON，可以原样导回去（只含条目，不含账号和设置）。
- **整库备份**：`npx wrangler d1 export DB --remote --output backup.sql`（含账号、日志、设置的哈希，**别公开**）。
- **时间点恢复**：D1 自带 Time Travel，一直开着（免费版保留 7 天，付费版 30 天）。`npx wrangler d1 time-travel info javbus-community` 看当前的恢复点，
  `npx wrangler d1 time-travel restore javbus-community --timestamp=<Unix 时间戳>`（或 `--bookmark=<ID>`）恢复。注意它恢复的是整个库，包括账号和设置。

### 应急：站长的访问密钥丢了、又没有第二个站长

清空账号表，再用 `SETUP_TOKEN` 重新创建站长（条目、举报、设置都不受影响，日志里的操作人名字会保留）：

```bash
npx wrangler d1 execute DB --remote --command "DELETE FROM users"
```

然后打开后台，会回到「首次安装」页。**这会删掉所有账号（包括其他维护者和他们的 App 口令）**，他们需要重新被邀请；清库前发出去的旧邀请会自动失效（发邀请的账号没了，邀请就不能用，不会被人抢在你前面用掉）。

## 安全设计

- **登录**：256 位随机访问密钥（`jck_…`）+ 可选 TOTP。库里只存 SHA-256；登录按 IP 限频（10 分钟 30 次），验证码 10 分钟内最多试 5 次（先原子占名额再校验，输对清零）。
- **会话**：随机令牌（只存哈希）放在 `HttpOnly` + `SameSite=Strict` 的 cookie 里，14 天过期；除本机 `http://localhost` 一类以外一律带 `Secure`（宁可没开「始终使用 HTTPS」的域名登录不上，也不下发明文也会跟着走的会话）；账号被停用 / 换密钥立刻失效。
- **CSRF**：所有改数据的请求必须带自定义请求头 `X-JC-Admin`，带了 `Origin` 的还必须和本站一致。
- **后台页面**：CSP 只允许同源脚本（`admin/public/_headers`），`X-Frame-Options: DENY`，不渲染任何服务端来的 HTML。
- **封面代理**：JavBus 的封面不带它自己站的 `Referer` 一律 403（防盗链），浏览器直接加载必然失败，所以后台的封面由服务端带上 `Referer` 去取再转回（`GET /api/admin/items/:id/cover`）。
  只代理库里条目自己的封面、只给登录的维护者，不是开放代理；只回位图（不回 SVG），响应头带 `default-src 'none'` 的 CSP。细节见 [docs/architecture.md](docs/architecture.md)。
- **App 提交**：设备号、IP 都只存加盐哈希（盐是库里随机生成的），不存明文；我们自己打的日志里没有 IP 和请求体，平台自带的每请求调用日志也关了。
  （加盐哈希的保护有限：盐和哈希在同一个库里，有库的人可以穷举 IPv4 反推 IP；它的作用是后台不展示 IP 明文、不随手留下明文，不是对抗拿到整个库的人。）
  条目的地址只收公网网站的域名（拒绝 IP 字面量、localhost、内网后缀）。这是字面量检查，拦不住指向内网的域名（比如 `127.0.0.1.nip.io`）和重定向；好在 Workers 平台本身到不了私网，实际影响很小。
- **滥用防护**：按设备 / IP 限频（IPv6 按 /64 一段算一个 IP，同一段里换地址绕不过）、每天总闸、举报按「不同的 IP」算人数（作者精选不自动隐藏）、屏蔽词（先 NFKC、去掉看不见的字符再比，全角 / 夹隐形字符绕不过）、
  网站名单、封禁、列表条数和字节数上限、请求体大小上限（提交 8 KB、导入 1.5 MB、流式读取不会把大包吞进内存）、口令连续试错 20 次 / 小时后限速。
  已知局限：同一个出口 IP 后面的人（学校 / 公司 / 运营商级 NAT）共用限频和举报人数。
- **不做的**：没有验证码（Turnstile）。App 是原生脚本，没法弹验证；真被刷了靠限频、封禁、网站名单和「先审核再公开」。

| 部署时报找不到数据库 / 提示要 `database_id` | 第一次 `npm run deploy` 会自动建库；没建成就手动 `wrangler d1 create javbus-community` 再填 `database_id` |
| 接口返回 500 / 表不存在 | 迁移没应用：`npm run db:migrate`（线上）/ `npm run db:migrate:local`（本地） |
| 脚本里「测试连接」连不上 | 地址对不对（不带末尾斜杠）；`workers.dev` 在部分网络下要走代理，或者绑自己的域名 |
| 定时检查没动静 | 后台「设置」里的「开启自动检查」；「检查」页最近的运行记录；Cloudflare 后台 → Worker → Logs 里找 `check_batch` 那行日志 |
| 条目检查全是「存疑」 | 站点在拦机器访问（403 / 验证页），属于预期；看「检查」页里的详情文字 |
| 后台的封面全显示「加载失败」 | 部署的是不是带封面代理的版本（浏览器开发者工具里封面请求应该是 `/api/admin/items/…/cover`）；是的话多半是 Cloudflare 的出口被图床拦了，和检查结果里「封面 HTTP 403」同一个原因 |
| 列表满了，新提交一直收到 `FULL` | 设置里调大「每份列表的条数上限」（最多 8000），或者隐藏 / 删除一些旧条目 |
| 日志在哪看 | Cloudflare 后台 → Workers & Pages → 你的 Worker → Logs；本地是 `wrangler dev` 的终端输出。只有我们自己打的几行 JSON（`event` 字段区分：`check_batch`、`housekeeping`、`unhandled_error`……），不含 IP 和请求体。平台自带的「每个请求一条」的调用日志默认关了（`wrangler.jsonc` 里 `invocation_logs: false`，免费版每天只有 20 万条日志额度、保留 3 天），要排查具体请求时临时打开 |
