# 设计取舍

这份文档记录「为什么这么写」。接口细节看 [api.md](api.md)，部署和使用看 [../README.md](../README.md)。

## 目标和约束

- **谁在用**：几十到几千个 JavBus 脚本用户（只读列表、偶尔提交 / 举报）+ 几个到十几个维护者。
- **要跑在 Cloudflare 免费版上**：这是最硬的约束，下面大部分设计都是它推出来的：

  | 限制 | 免费版 |
  | --- | --- |
  | Worker 请求 | 10 万 / 天 |
  | 每次调用 CPU | 10 毫秒（等外部请求 / D1 的时间不算） |
  | 每次调用子请求 | 50 个 |
  | 每次调用 D1 查询 | 50 条 |
  | D1 | 500 万行读、10 万行写 / 天；单行最大 2 MB；一条语句最多 100 个绑定参数 |
  | Cron 触发器 | 每账号 5 个 |
  | 日志 | 20 万条 / 天，保留 3 天 |

  （数字来自 Cloudflare 官方文档，以文档为准。）
- **没有可信的客户端**：App 是公开的脚本，谁都能伪造请求。所以任何「设备号」「口令」都只是软约束，真正的防线是限频、审核和封禁。
- **隐私**：不存 IP 和设备号的明文，只存加盐哈希；日志里没有请求体。

## 数据模型

`migrations/0001_init.sql` 里有注释。一句话版本：

| 表 | 作用 |
| --- | --- |
| `users` / `app_keys` / `sessions` / `invites` | 维护者账号：访问密钥登录（只存哈希）、App 口令（给脚本的作者通道用）、会话、邀请 |
| `items` | 推荐条目。`channel`（网友 / 作者精选）+ 番号唯一（不分大小写）；状态 待审 / 已上线 / 已拒绝 / 已隐藏；带检查结果和举报数 |
| `reports` | 举报；`(item_id, reporter)` 唯一（同一个设备对同一个条目只一条）；条目的「举报数」= 没处理的举报里**不同的 IP** 有几个 |
| `banned` | 封禁：设备 / IP（哈希）/ 番号 |
| `snapshots` | 公开列表的快照（每个频道一行） |
| `settings` / `audit_log` / `check_runs` / `rate_limits` | 站点设置（一项一行 JSON，外加一个内部用的 `_salt`）、操作日志、检查记录、限频计数 |

## 公开列表是一行快照

App 读列表的次数远多于任何别的操作，而且每次都要整份。所以：

- 条目变化（上线 / 隐藏 / 编辑 / 删除 / 导入……）时，**在同一个 `db.batch`（同一个事务）里**重建这个频道的快照：
  一条 `INSERT … SELECT json_group_array(json_object(…)) … ON CONFLICT DO UPDATE`，数据不进 Worker——免费版 10 毫秒 CPU 经不起在 JS 里拼 3000 条 JSON。
- 读列表只读这一行（`SELECT version, count, bytes, body`），响应带 `ETag: W/"user-17"`（`17` 是快照版本，每次重建 +1），`Cache-Control: no-cache`——
  客户端每次都来确认，没变就 304。不用 Cache API / Workers Cache：workers.dev 域名上它不生效。
- **顺序**：最新上线的在最前。靠外层聚合时 SQLite 不会把带 `ORDER BY` 的子查询拍平这条规则保证确定性，测试里有一条专门盯着。
- **2 MB 保护**：D1 单行最大 2 MB。快照记下自己的字节数，收稿 / 上线前检查「条数没到上限、字节数没到 1.8 MB」，到了返回 `FULL`。
- **自愈**：个别流程（举报自动隐藏、检查自动隐藏）是「先改条目、再重建快照」两步，万一中间被中断，每天凌晨的清理会把两份快照无条件重建一遍。

## 一致性：什么在事务里

凡是「改条目 + 重建快照 + 记操作日志」的操作都放进同一个 `db.batch`：要么都成，要么都不成。`src/lib/items.ts` 里是统一的写法。例外只有两处（见上面的自愈），
都是自动触发的后台动作，不影响维护者操作的一致性。

D1 的两条限制决定了几种写法：

- 一条语句最多 100 个绑定参数 → 「一批 id」打成一个 JSON 数组参数，用 `json_each()` 展开；批量导入也是一条 `INSERT … SELECT … FROM json_each(?)`。
- 一次调用最多 50 条查询 → 批量操作的日志合成一条，不是一个条目一条；每个接口只用几条语句。

## 认证

- **访问密钥而不是密码**：256 位随机数，库里只存 SHA-256。随机密钥不需要慢哈希；而且免费版每个请求只有 10 毫秒 CPU，PBKDF2 / scrypt 放不进去。
  代价是「用户记不住」——所以靠密码管理器；丢了由站长重置。
- **会话**：随机令牌（只存哈希）放在 `HttpOnly` + `SameSite=Strict` 的 cookie 里，14 天固定过期（不续期：登录只是粘贴一个密钥，很便宜）。
  每次请求都会重新读账号，所以改角色 / 停用立刻生效。
- **CSRF**：`SameSite=Strict` 之外，改数据的请求还要带自定义头 `X-JC-Admin`，带了 `Origin` 的必须和本站一致。
- **TOTP**：可选；开了以后登录要「密钥 + 验证码」，10 分钟内最多试 5 次：**先原子地占一个名额（一条 upsert）、再校验**，输对了清零——「先读计数、失败了再 +1」的话，并发的一批请求都在计数涨起来之前读到「没超限」，等于没有限制。
  已知局限：同一个验证码在有效期内可以重复使用（没做一次性保护）。
- **邀请**：令牌一次有效、会过期；接受邀请时先在一条语句里「占住」（`UPDATE … WHERE used_at IS NULL AND expires_at > ?`），再建账号，账号建失败（重名）就把邀请放回去。
  邀请的权限**跟着发邀请的人走**：加入时还要核对他还在、没被停用、现在的权限还够发这个角色的邀请（只有站长能邀请管理员）；他被停用 / 改角色时他没用过的邀请也一并删掉。
  只看「没过期」的话：被盗的站长账号停用后，他之前发的管理员邀请还能留后门；按 README 的应急办法清空账号表后，旧邀请会先于真站长被人用掉、把安装页占掉。
- **App 口令**（`jca_`）：给脚本的作者通道和「撤销别人的推荐」用，等于「审核条目」的权限；每人自己生成、随时撤销，账号停用自动失效；站长重置某人的访问密钥时一并撤销（账号被盗期间攻击者可能已经生成了自己的口令）。
- **账号名**：先 NFKC 规整（全角 → 普通字母），不能含看不见的字符，`system` / `app` 是保留名（操作日志里 actor 用它们表示定时任务和脚本里的提交，注册成这两个名字就分不清是人还是系统）。
  唯一性靠 SQLite 的 `COLLATE NOCASE`，它只折叠 ASCII 大小写，非 ASCII 的大小写写法（`É` / `é`）会被当成两个名字——对一个小团队的维护者账号，这个缺口可以接受。
- **首次安装**：`POST /api/admin/setup` 凭服务端机密 `SETUP_TOKEN` 创建第一个站长（`INSERT … WHERE NOT EXISTS (SELECT 1 FROM users)`，只能成功一次）；
  按 IP 限频；之后永久关闭。没设 `SETUP_TOKEN` 时直接拒绝并告诉你去设置。

## 限频

固定窗口计数存在 `rate_limits` 表：key = `名字#窗口编号`，一条多行 upsert（`INSERT … ON CONFLICT DO UPDATE SET count = count + 1 RETURNING`）同时给设备 / IP 的小时 / 天几个计数 +1，
再比较有没有超限。被拒绝的请求也计数，一直撞的客户端会一直被拒。每天凌晨清掉过期的行。

- **IP 的算法**：只信 Cloudflare 边缘写的 `CF-Connecting-IP`；IPv6 按 /64 归并（`normalizeIp`）。家庭 / 机构拿到的是整段 /64，后 64 位想换多少个就换多少个，按完整地址算的话限频和封禁都形同虚设。
  设备号是 App 自己报的、谁都能编，所以设备号只是「软」的一层，IP 才是防线。
- **每天总闸**（`submitPerDayGlobal`，默认 300）：每条新提交上线都要重读整份列表来重建快照（3000 条 ≈ 3000 行读），免费版 D1 每天只有 500 万行读额度，不设总闸的话换设备号 / IP 就能把额度刷光、连 App 读列表都失败。
  **只数走到最后一步的提交**（已经过了封禁、按设备 / IP 限频、校验、查重、容量）——被前面拦下的请求不占名额，不然一个人狂发请求就能把当天的名额耗光。维护者带口令提交不受限。
- **匿名提交不写操作日志**：每条都写一行会把日志刷爆，翻页时的 COUNT 也要扫一大片；条目本身带着提交者哈希和时间。翻页的总数还封顶 10000。

## 举报怎么算人数

条目的「举报数」= 没处理的举报里**不同 IP** 的个数，不是举报条数：设备号是客户端自己报的，一个人换三个设备号就是三条举报，按条数算的话一个人就能把条目刷下架——作者精选也一样，而且番号能从公开列表里枚举。
举报行本身都留着（给维护者看原因和详情）。数到阈值只自动隐藏**网友推荐**；**作者精选**是维护者挑的，不该被匿名举报直接下架，只进待复核。
维护者对条目的任何处理都会关掉它没处理的举报并清零计数（隐藏 / 拒绝 = 已处理，通过 = 驳回），否则被自动隐藏的条目通过后，残留的计数会让下一个人一举报就又被隐藏。

不用 Workers 自带的 Rate Limiting 绑定：需要额外开通，而且 D1 计数的开销就是多一条语句，免费版绰绰有余。

## 自动检查

每个地址的结论有四种（`src/lib/checks.ts` 文件头有说明）：**正常**（2xx，封面还要是图片）、**失效**（404 / 410）、**存疑**（其它一切）、**没法检查**（详情页被年龄验证页挡住）。
条目的结论：有失效 → 失效；有存疑 → 存疑；至少一项正常 → 正常；**一项都没法判断 → 没查成（`unchecked`）**——不能记成「正常」，那会清零失效计数、还会把因失效隐藏的条目放回公开列表。
原因：目标站点常有 Cloudflare 验证页，对机器返回 403 / 503，这不能当成失效；只有明确的 404 / 410 才算，并且要**连续**几次才自动隐藏。

自动隐藏的代价是整站条目被下架，所以有三道保险：① 连续 N 次失效才隐藏；② 「连续」要隔得开——两次失效之间至少隔半个复查间隔才都算数（手动连点几次「检查一批」不会几分钟内凑够 N 次）；
③ 一批里几乎全判成失效（≥ 5 条且 ≥ 80%）整批改判存疑、不累计——多半是站点在拦我们（对数据中心 IP 回 404 / 410）或网络出了问题，让维护者人工看比自动下架稳妥。手动指定几个条目来查时不做这一条。

**JavBus 的详情页是个特例**（2026-10-22 用 curl 实测）：没有年龄验证 cookie 时，所有详情页——不管番号存不存在——都 302 到 `/doc/driver-verify` 并返回 200。
如果照常判，链接永远是「正常」，是个假信号；所以检查器认出落在验证页上的响应，把这一项标成「没法检查」、不参与判定，对 JavBus 实际只看封面。
这里没有选择给检查器带上验证用的 cookie：那等于替机器静默确认「已满 18 岁」，和脚本那边「先问用户、同意才提交」的立场不一致，而且封面这个信号已经够用。

- **预算**：每个条目最多 2 个请求（封面 + 链接），不读响应体（拿到状态码和响应头就 `cancel()`，不占外连名额也不下载整张图）；同时最多 3 个条目并行
  （Workers 同一时刻最多 6 个外连）；一批最多 25 个条目（免费版一次调用最多 50 个子请求；`checkBatchSize` 和手动的 `limit` 都封顶在 25，指定 `itemIds` 时有几个查几个）。
  万一子请求额度还是用完了（`Too many subrequests`），没发出去的条目这次**不算查过**——不记结果、不动检查时间和失效计数，运行记录里写明；不会被记成「网络错误」然后一个复查间隔内都不再查。
- **选哪些**：已上线的 + 因失效被自动隐藏的（后者恢复了要能自动放回来）；从没查过的优先，然后是最久没查的。手动隐藏的不在范围内。
- **「全部检查」由前端驱动**：后端每次只处理一批（一次调用的预算就这么多），前端记下「这一轮开始的时刻」，反复调 `POST /checks/run {olderThan: 开始时刻}`，
  直到 `remaining` 为 0——「这个时刻之后还没查过」天然保证每个条目一轮只查一次，不需要在服务端记状态。
- **并发的两个人同时点**：会挑到同一批、各查一遍，浪费但无害（结果都是最新的）。
- **一次检查的写入**：`UPDATE … FROM (SELECT … FROM json_each(?))` 一条语句落完所有结果，再一条语句处理自动隐藏 / 恢复；检查记录先写一行再补结果，
  被中断的记录由每天的清理标成「中途中断」。

## 后台的封面为什么要经服务端

JavBus 一类站点的封面靠 `Referer` 防盗链：不带、或者带的不是它自己的站，一律 403（2026-10-23 实测 www / pics / images.javbus.com 都这样，带 `https://www.javbus.com/` 才给图；`images.javbus.org` 要带 `https://www.javbus.org/` 或者不带）。浏览器从后台页面加载图片，`Referer` 只能是后台自己的地址或者不带，所以直接 `<img src>` 必然失败。

- **做法**：`GET /api/admin/items/:id/cover` 按条目 id 取库里的 `src` / `link`，带详情页所在站的 `Referer` 去取（和自动检查一致），被 403 再换封面自己所在的站试一次，成功就把图片流原样转回（不读进内存，几乎不占 CPU）。
- **不是开放代理**：只代理库里条目自己的封面，只给登录的维护者；地址入库时校验过只收公网域名，取之前再查一遍。
- **不让它变成 XSS 的跳板**：只回位图（SVG 能带脚本，不回）；响应头照 GitHub camo（同类的图片代理）收紧：`default-src 'none'` 的 CSP、`nosniff`、`X-Frame-Options: DENY`、`Cross-Origin-Resource-Policy: same-origin`。
- **额度**：显示一张封面 = 1 次请求 + 最多 2 个子请求；浏览器缓存一天（地址里带封面地址的哈希，地址改了才重新取）。维护者翻后台的量远小于 App 读列表，免费版的请求数够用。
- **前提**：Cloudflare 的出口能拿到对方的图（2026-10-23 线上实测：JavBus 的封面能拿到，后台显示正常）。哪天被站点拦了，后台会显示「加载失败」，和自动检查里的「存疑」是同一个原因。

## 为什么不用别的

- **Durable Objects**：限频和计数用 D1 一条语句就够，不需要为它引入另一种存储；没有需要「每个房间一个协调者」的场景。
- **KV**：最终一致，列表更新后各地读到旧数据的窗口不可控；快照放 D1 一行，ETag 随版本走，行为确定。
- **Queues / Workflows**：检查一批的工作量小到一次调用就做完，定时任务 + 手动触发已经够了。
- **Turnstile 之类的验证码**：App 是原生脚本，没法弹验证。
- **zod 等校验库**：校验就那几个字段，手写比引入依赖更小更快，错误信息也是中文、能直接给人看。

## 以后想加什么、怎么加

- **通知维护者**（新待审 / 新举报推到 Telegram）：在 `createItem` / `createReport` 之后 `ctx.waitUntil(fetch(…))`，机密放 `wrangler secret`。现在没做：没人要求，也多一份机密要保管。
- **条目更多 / 更大**：快照整份存一行是上限所在（2 MB）；超过 8000 条要改成分页读（App 端也要跟着改）。
- **付费版**：调大「每次检查几个条目」，把 `checkBatchSize` 上限放开，其它设计不用动。
- **后台多语言 / 主题**：前端是纯 Preact，文案集中在各页面里；现在只有中文。

## 已知局限（知道、没做、或者做不了）

- **TOTP 验证码可重复使用**：同一个码在有效期（约 90 秒，前后各容许一档）内能用多次。要做得记下每个账号最后用过的时间片，需要加一个列；对「得先知道访问密钥」的攻击面来说价值有限，没做。
- **同一个出口 IP 后面的人共用限频和举报人数**（学校 / 公司 / 运营商级 NAT）。限频的上限别设太小；举报要 3 个**不同的 IP** 才自动隐藏，一个出口后面的多个人只算一个。
- **没有 `CF-Connecting-IP` 时**（只会出现在自己架反向代理的场景，Cloudflare 边缘一定会带）所有请求共用一个 `unknown` 桶，限频会互相影响。
- **两个人同时提交同一个番号**：一个 `succeed`、一个 `RE`，但输家的那次也会多重建一次快照（版本号多涨 1，客户端白白多下载一份）。无害，没做条件化——那要依赖 `changes()` 在 D1 批处理里的行为，没法在线上验证，万一不对会让正常提交的快照悄悄不重建，得不偿失。
- **改条目的几个路径用事务外读到的旧状态决定要不要重建快照**：毫秒级窗口，万一漏了，每天凌晨的清理会补上。
- **账号名唯一性只折叠 ASCII 大小写**（见「认证」）。
- **访问密钥只在响应里出现一次**：建号 / 重置时服务端写库成功、但后面几次 D1 调用失败的话，响应是 500、密钥丢了——首次安装会因此被「已经有站长了」挡住，走 README 的应急办法（清空账号表）；其它情况让站长重置密钥。
- **清空 `settings` 表会让盐重新生成**：之前所有的封禁和「自己撤销自己提交的」都对不上了（库里存的哈希是用旧盐算的）。
- **地址校验是字面量检查**：拦得住 IP 字面量、`localhost`、内网后缀，拦不住指向内网的域名（`127.0.0.1.nip.io`）和重定向。Workers 平台本身到不了私网，所以实际影响小，但别把它当成 SSRF 防线。
- **自动检查对 JavBus 只看封面**（见「自动检查」）；Cloudflare 的出口去访问 JavBus 会不会被拦，没法在本地验证。
- **CPU 毫秒数没在真实环境量过**：本地模拟的运行时不限 CPU。已经把明显的大头（导出 / 导入 / 快照）搬进 SQL 或分批，真实占用要部署后在 Cloudflare 后台看。
